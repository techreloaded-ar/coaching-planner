# US-041: Bootstrap idempotente dell'amministratore iniziale al deploy — Piano di Implementazione

**Generato da:** ARchetipo Planning Team
**Data:** 2026-07-22

---

## Spec

**Epic:** EP-000 — Fondazione del Progetto
**Priorità:** HIGH | **Punti:** 2

**Storia Utente**
Come operatore che porta Coaching Planner in staging e produzione, voglio che al deploy venga garantita — tramite la variabile d'ambiente `AMMINISTRATORE_INIZIALE_EMAIL` e uno script idempotente eseguito nella stessa fase delle migrazioni — l'esistenza di un utente con quell'email e ruolo `AMMINISTRATORE`, così che ogni nuovo ambiente sia accessibile da subito senza censire manualmente il primo amministratore nel database.

**Criteri di Accettazione**
- AC-1 — Con variabile valorizzata ed email non censita, lo script crea un `Utente` con quell'email, ruolo `AMMINISTRATORE`, stato attivo e nome predefinito non vuoto, terminando con successo e dandone evidenza in output
- AC-2 — Se l'email è già censita (qualunque ruolo o stato), lo script termina con successo senza creare, modificare o cancellare dati, segnalando che l'utente esiste già
- AC-3 — Se la variabile manca o è vuota, lo script termina con errore nominando `AMMINISTRATORE_INIZIALE_EMAIL`, senza alcuna scrittura sul database
- AC-4 — La sequenza di deploy documentata esegue il bootstrap nella stessa fase di `prisma migrate deploy`, prima che l'applicazione serva traffico
- AC-5 — La guida di deploy sostituisce il passo manuale con la nuova variabile e il nuovo comando, e la checklist riflette il processo automatico

---

## Soluzione Tecnica

Nuovo script CLI idempotente `scripts/bootstrap-amministratore-iniziale.ts`, costruito sui pattern già presenti nel repository, agganciato al build command Vercel subito dopo `prisma migrate deploy`.

- **Struttura testabile** sul modello di `scripts/siteground-connectivity-check.ts`: funzioni esportate pure/iniettabili (`validaEmailAmministratoreIniziale`, `eseguiBootstrapAmministratoreIniziale`) più entry point CLI guardato da `process.argv[1]`, così i test unitari importano le funzioni senza eseguire il comando.
- **Accesso al database** sul modello di `prisma/seed.ts`: `PrismaClient` con adapter `PrismaPg` e import relativo `../src/generated/prisma/client` (i path alias `@/` non servono negli script). La funzione di bootstrap riceve però un client iniettato con interfaccia minima (`utente.findUnique` / `utente.create`) per la testabilità.
- **Ordine delle operazioni per AC-3**: l'entry point valida `AMMINISTRATORE_INIZIALE_EMAIL` (trim; errore se assente o vuota) PRIMA di istanziare qualunque client Prisma — così l'uscita in errore avviene senza aprire connessioni né scrivere. `DATABASE_URL` mancante produce un errore distinto e chiaro (stesso tono di `src/lib/db.ts`).
- **Normalizzazione email** coerente con `creaUtente` (`src/app/(back-office)/anagrafiche/utenti/actions.ts`): `trim()` + `toLowerCase()` sia per la ricerca sia per la creazione.
- **Dati creati**: `nome: "Amministratore Iniziale"` (costante esportata, non vuota → AC-1), `ruolo: AMMINISTRATORE`; `attivo = true` arriva dal default di schema. Nessun `Account`, `Collaboratore` o notifica (fuori perimetro).
- **Caricamento env locale** con `loadEnvConfig(process.cwd())` di `@next/env` (già devDependency, stesso approccio di `vitest.config.ts`): la demo locale funziona senza toccare `.env`; su Vercel le variabili sono già nell'ambiente.
- **Aggancio al deploy**: build command Vercel documentato aggiornato a `prisma generate && prisma migrate deploy && npx tsx scripts/bootstrap-amministratore-iniziale.ts && next build` — stessa fase delle migrazioni, prima che l'app serva traffico (AC-4). `tsx` è disponibile in build perché devDependency installata da Vercel. Aggiunto anche lo script npm `db:bootstrap-amministratore` per l'uso manuale/demo.

### Decisioni Architetturali

Nessuna scelta supera la soglia ADR: lo script segue i pattern esistenti (script `tsx` testabile + adapter Prisma del seed) e l'aggancio al build command estende il meccanismo già deciso e documentato per `prisma migrate deploy`. Nessun nuovo ID decision.

**Assunzioni registrate**: nessuna validazione di formato dell'email (AC-3 richiede solo assente/vuota); il nome predefinito è la costante `"Amministratore Iniziale"`; `prisma/seed.ts` resta invariato come da fuori perimetro.
