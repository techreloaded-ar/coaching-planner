# US-002: Database PostgreSQL con Prisma, migrazioni e seed — Piano di Implementazione

**Generato da:** ARchetipo Planning Team  
**Data:** 2026-06-11

---

## Spec

**Epic:** EP-000 — Fondazione del Progetto  
**Priorità:** HIGH | **Punti:** 2

**Storia Utente**  
Come sviluppatore del progetto Coaching Planner, voglio un database PostgreSQL locale collegato all'applicazione tramite Prisma, con migrazioni versionate e dati di esempio, così da poter evolvere lo schema dati in modo controllato e sviluppare senza dipendere dal database di produzione.

**Criteri di Accettazione**
- [ ] Lo schema Prisma iniziale è versionato e le migrazioni si applicano con successo su un database locale vuoto
- [ ] Il comando di seed popola dati di esempio utilizzabili in sviluppo
- [ ] La connessione usa una DATABASE_URL configurata via variabili d'ambiente, distinta tra locale e produzione
- [ ] I tipi monetari nello schema usano Decimal, mai float

---

## Soluzione Tecnica

La spec introduce il livello dati PostgreSQL/Prisma sopra lo scaffold prodotto da US-001, mantenendo l'ambiente locale indipendente dalla produzione e versionando ogni evoluzione tramite migrazioni Prisma. La soluzione deve essere applicata dopo l'integrazione dello scaffold Next.js, perché riusa `package.json`, `.env.example`, `src/lib/` e la struttura di test predisposta dalla spec precedente.

- Configurare Prisma 6.x con provider `postgresql`, client generato e script npm dedicati (`db:migrate`, `db:deploy`, `db:seed`, `db:studio`), più un `docker-compose.yml` per un Postgres locale ripetibile.
- Definire uno schema iniziale coerente con il PRD: utenti con ruolo, collaboratori, clienti, offerte, attività, trasferte/scaglioni km e relazioni necessarie ai futuri consuntivi. Tutti i campi monetari e tariffari devono usare `Decimal`/`@db.Decimal`, mai `Float`.
- Versionare la prima migrazione Prisma e garantire che `prisma migrate dev` parta da database vuoto senza passaggi manuali.
- Implementare `prisma/seed.ts` con dati realistici di sviluppo: un amministratore, almeno un collaboratore, clienti, offerte con tariffe, scaglioni chilometrici e alcune attività dimostrative.
- Aggiornare la gestione ambiente: `.env.example` con `DATABASE_URL` locale, indicazioni per `.env.local` non committato e note README per distinguere locale, test e produzione.
- Aggiungere `src/lib/db.ts` come singleton Prisma Client riusabile da route/server action future, evitando istanze multiple in sviluppo con hot reload.

**Assunzioni operative**
- US-001 è già pianificata ed è attualmente in lavorazione: l'implementazione di US-002 deve partire solo quando lo scaffold è disponibile nel ramo principale o nel worktree di sviluppo previsto.
- La connettività al database SiteGround di produzione resta fuori scope di questa spec; qui si predispone solo la variabile `DATABASE_URL` e il flusso `prisma migrate deploy`.

---

## Strategia di Test

La verifica combina controlli automatici sulla modellazione Prisma, test di integrazione sul database locale e una prova applicativa minima della connessione tramite il client condiviso.

- Eseguire `prisma validate` e `prisma migrate dev` su un database locale vuoto per provare schema e migrazioni versionate.
- Eseguire `npm run db:seed` e verificare che i record di esempio coprano collaboratore, cliente, offerta, tariffa Decimal, attività e scaglione km.
- Aggiungere test Vitest/integration per importare `src/lib/db.ts`, interrogare un dato seedato e confermare che i campi monetari siano modellati come Decimal lato Prisma.
- Mantenere `npm run lint` e `npm run build` verdi dopo l'aggiunta di Prisma, seed e configurazioni.

### Test E2E — Simulazione Utente

Questa spec non introduce pagine o flussi utente nuovi, quindi non richiede nuovi scenari Playwright. La dimostrazione è da sviluppatore: avviare Postgres locale, applicare migrazioni, lanciare il seed e verificare dall'applicazione/Prisma Client che la connessione funzioni. Se US-001 ha già introdotto uno scenario e2e di fumo, mantenerlo verde ma non registrare un nuovo video per US-002.
