## Discovery Checklist for State-Changing Features

Before proposing any spec for a feature that changes the state of an existing entity (locks it, closes it, archives it, approves it, freezes it), walk through this checklist item by item. For every item: if the answer is in the request, the Wiki, or the code, state it; otherwise ask the client. Each item must end either in an acceptance criterion or in an explicit entry of the `Out of Scope` section. Never leave an item silently unaddressed.

1. **Who** may perform the state change, and who may undo it. Who can only see the state.
2. **Which instances or periods** are eligible: current, future, already in use, already affected by downstream processes.
3. **Every existing write path** on the entity and on its children: list them from the code (server actions, forms, batch operations, duplications, moves, deletions, related sub-records) and state the effect of the new state on each one, including for privileged roles.
4. **Reversibility**: can the change be undone, by whom, and what must accompany the undo (reason, confirmation, record).
5. **History**: whether each change and undo must be recorded with author and time, and whether the full history or only the last state is kept.
6. **Visibility** in every view that shows the entity or its children: list the views from the code (lists, calendars, detail pages, reports, exports) and state what each one shows and which actions it hides.
7. **Concurrent operations**: what happens to a write that is in flight while the state changes, and after it.
8. **Clients with stale data**: what a user sees when they act on a screen loaded before the state change (cached pages, open forms, open tabs).
9. **Invariance of existing data**: the state change must not alter, recompute, or delete existing records or derived figures; say which ones must stay identical.

Group the open questions in as few messages as possible, but do not skip an item because it seems minor.
